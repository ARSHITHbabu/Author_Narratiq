# Incident Report — NarratIQ AI unreachable at `https://2e5wiiphzhzf14-3000.proxy.runpod.net`

| Field | Value |
|---|---|
| **Incident** | Frontend returns HTTP 404 at the public RunPod URL despite startup script reporting "READY" |
| **Date** | 2026-07-24 |
| **Pod ID** | `2e5wiiphzhzf14` (`coloured_gray_emu`, EU-SE-1) |
| **Severity** | Blocking — application completely inaccessible from the browser |
| **Status** | Root cause confirmed; fix identified |
| **Confidence** | 100% (confirmed against RunPod's own API) |

---

## 1. Executive Summary

**The application is not broken. The port is not exposed.**

Next.js is running correctly, bound to all interfaces on port 3000, and serving a full HTTP 200 HTML response locally. The backend, vLLM, and BGE-M3 are all healthy. Nothing inside the container is failing.

The 404 is generated by **RunPod's Cloudflare edge proxy**, before the request ever reaches the pod. The pod was created with only three ports exposed — TCP 22, HTTP 8888, HTTP 19123. Ports **3000 and 8000 are not in the pod's port configuration**, so `*-3000.proxy.runpod.net` has no upstream to route to and the edge returns a bare 404.

There is a **second, latent failure** behind this one: port 8000 is equally unexposed, so `NEXT_PUBLIC_API_URL=https://2e5wiiphzhzf14-8000.proxy.runpod.net` will also 404. Exposing only 3000 would give you a UI that loads and then fails every API call.

  {"privatePort": 19123, "publicPort": 60727, "type": "http"}

**Ports 3000 and 8000 are absent from the pod configuration.**

Corroborating live tests:

| URL | Status | Meaning |
|---|---|---|
| `…-3000.proxy.runpod.net` | **404** | not exposed |
| `…-8000.proxy.runpod.net` | **404** | not exposed — *backend also unreachable* |
| `…-3001.proxy.runpod.net` | **404** | not exposed |
| `…-8888.proxy.runpod.net` | **302** | exposed (Jupyter) — proves the proxy mechanism itself works |

**How RunPod's HTTP proxy works:** `https://{podId}-{port}.proxy.runpod.net` is not a dynamic port forwarder. RunPod maintains a routing table populated **only** from the pod's declared HTTP port list, set at pod creation (or via Edit Pod). Cloudflare looks up `{podId, port}`; a miss returns an empty-bodied 404 at the edge. Whether anything is listening inside the container is never consulted. The 302 from 8888 versus 404 from 3000 is a clean A/B proof of exactly this.

**Environment variables:** `frontend/.env.local` contains `NEXT_PUBLIC_API_URL=https://2e5wiiphzhzf14-8000.proxy.runpod.net` — correctly formed, but pointing at an unexposed port. No `PORT`/`HOST` overrides present. `RUNPOD_POD_ID=2e5wiiphzhzf14` matches the URL, so the pod ID is correct.

## 3. Root Cause

**What is wrong:** The RunPod pod's HTTP port configuration does not include 3000 or 8000. Only 22/tcp, 8888/http, and 19123/http are exposed.

**Why it happened:** The pod was launched from a template (an InvokeAI / Stable-Diffusion image — its bundled nginx proxies 3001→3000, 8001→8000, 7861→7860, 9091→9090) whose port list was never adjusted for NarratIQ's 3000/8000 layout. Exposed ports are fixed at pod-creation time and cannot be inferred from what later starts listening. `start-narratiq.sh` composes the public URL by **string interpolation** from `$RUNPOD_POD_ID` and `$FRONTEND_PORT` (lines 31–32) — it constructs a URL that is *syntactically* right and *never verifies it resolves*.

**Confidence: 100% — confirmed.** Direct evidence:

1. RunPod's API returns the authoritative port list omitting 3000.
2. The 404 carries `server: cloudflare` with a zero-length body and none of Next.js's response headers.
3. Exposed port 8888 returns 302 through the identical proxy path while 3000 returns 404.

## 5. Recommended Fix

### Option A — Expose the ports (correct permanent fix)

RunPod's port list is immutable on a running pod, so this needs a restart:

1. RunPod Console → your pod → **Edit Pod**
2. **HTTP Ports** field: change `8888` to `8888,3000,8000`
3. Save → **Stop Pod** → **Start Pod** (the restart is required for the routing table to update)
4. After boot: `bash /workspace/narratiq-ai/start-narratiq.sh`

> The pod ID normally survives a stop/start. If RunPod issues a new one, re-run the startup script — it regenerates `.env.local` and `CORS_ORIGINS` from `$RUNPOD_POD_ID` automatically (lines 31–32, 445).

Both ports are required: 3000 serves the UI, 8000 serves the API the browser calls directly.

### Option B — SSH tunnel (works right now, no restart, no data loss)

TCP 22 is already exposed at `194.68.245.208:22089`. From your local machine:

```bash
ssh -N -L 3000:localhost:3000 -L 8000:localhost:8000 root@194.68.245.208 -p 22089
```

Then, **inside the pod**, repoint and rebuild the frontend — `NEXT_PUBLIC_API_URL` is inlined at build time, so an edit alone is not enough:

```bash
cd /workspace/narratiq-ai/frontend
echo 'NEXT_PUBLIC_API_URL=http://localhost:8000' > .env.local
npm run build
fuser -k 3000/tcp; sleep 2
npm start -- --port 3000 > /tmp/narratiq-logs/frontend.log 2>&1 &
```

Open `http://localhost:3000`. Note this rebuild ties the frontend to the tunnel — revert `.env.local` to the proxy URL and rebuild once Option A is in place.

### Fix the false-success gate (either way)

`start-narratiq.sh:602` currently proves only that the loopback works. Add a public-URL probe after the local check so the script can never again announce a URL it hasn't tested:

```bash
if [ -n "$RUNPOD_POD_ID" ]; then
  PUB_CODE=$(curl -so /dev/null -w "%{http_code}" --max-time 15 "$FRONTEND_PUBLIC_URL" || echo 000)
  if [ "$PUB_CODE" = "404" ]; then
    echo "  ERROR: $FRONTEND_PUBLIC_URL returned 404 from the RunPod edge."
    echo "         Port ${FRONTEND_PORT} is NOT in this pod's HTTP Ports list."
    echo "         Fix: Edit Pod -> HTTP Ports -> add ${FRONTEND_PORT},${BACKEND_PORT} -> restart."
  elif [ "$PUB_CODE" != "200" ] && [ "$PUB_CODE" != "302" ]; then
    echo "  WARNING: public URL returned HTTP $PUB_CODE (local check passed)"
  fi
fi
```

## 7. Preventive Recommendations

**Validate what you advertise.** The core lesson: the script tested `localhost` and printed a public URL. Any readiness check must probe the exact URL it hands the user. The Phase 6 patch above closes this.

**Assert infrastructure preconditions at startup.** Add an early check in `start-narratiq.sh` that queries the RunPod API for the port list and fails loudly *before* spending ~70 seconds loading models:

```bash
PORTS=$(curl -s -X POST "https://api.runpod.io/graphql?api_key=$RUNPOD_API_KEY" \
  -d '{"query":"query { pod(input:{podId:\"'"$RUNPOD_POD_ID"'\"}) { runtime { ports { privatePort } } } }"}')
for p in "$FRONTEND_PORT" "$BACKEND_PORT"; do
  echo "$PORTS" | grep -q "\"privatePort\":$p" || echo "  FATAL: port $p not exposed on this pod — add it in Edit Pod and restart."
done
```

**Document the port contract.** Add to `CLAUDE.md`: *"This pod must expose HTTP ports 3000 and 8000. Ports are fixed at pod creation; changing them requires a stop/edit/start. A 404 with `server: cloudflare` and an empty body always means the port is unexposed — never an application fault."*

**Teach the 404 signature.** Bake the diagnostic into the runbook, since it's a 5-second triage:

| Symptom | Culprit |
|---|---|
| 404, `server: cloudflare`, `content-length: 0` | Port not exposed on the pod |
| 404 with `X-Powered-By: Next.js` | Genuine application routing issue |
| 502 / 522 | Port exposed, but nothing listening inside |

**Prefer a single exposed port.** Exposing two ports doubles this failure mode. Proxying `/api/*` from Next.js to `localhost:8000` via `rewrites()` in `next.config.js` would collapse the surface to one port, and eliminate the browser-facing CORS configuration entirely.

**Process supervision.** All three services run as bare background jobs — a crash after startup leaves no supervisor to restart or alert. `supervisord` or systemd units with restart policies would close that gap.
