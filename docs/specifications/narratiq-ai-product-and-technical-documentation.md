## Architecture Principle — Production-First

NarratIQ has one architecture, and it is production-grade. No feature is a temporary prototype or a future rewrite candidate. Three rules follow from this and are enforced in code, not just stated:

1. **Self-hosted only.** Every model runs on the operator's own GPU pod. No manuscript text is sent to any external AI service, and there is no telemetry.
2. **The author owns the words.** AI output is a proposal. Nothing replaces chapter text without the author accepting it. Unpinned generations are never stored (Phase 3 rule R1).
3. **Honest states.** Operations report `completed`, `partial` or `failed` from what actually happened, and the API never returns success for work that did not succeed.

## 1. Executive Summary

### 1.1 What NarratIQ AI is

NarratIQ AI is a self-hosted creative-writing studio for long-form fiction. It supports the whole lifecycle of a manuscript, from story intake and genre detection, through chapter writing with memory-aware AI assistance, to analysis and export. It is positioned as **co-intelligence, not an AI writer**: the author remains the creative force, and NarratIQ handles consistency, recall and analysis at manuscript scale.

### 1.2 The problem it solves

- Grammar tools fix surface errors but understand nothing about the story.
- General chat assistants have no persistent memory of a 100,000-word manuscript.
- Organisational writing software has no intelligence.
- Developmental editing costs thousands per manuscript.
- No single tool covers intake → memory-aware writing → analysis → export, and handwritten or spoken notes have no route into the manuscript.

## 2. Technology Stack and Architecture

### 2.1 Service topology

```
vLLM :9001        →   FastAPI :8000                          →   Next.js 14 :3000
(Qwen2.5-7B)          (+ BGE-M3 in-process, faster-whisper,       (same-origin /api/* proxied
                       GOT-OCR2.0, PostgreSQL 16 + pgvector)        to the backend)
```

- The browser talks only to the frontend's origin. Next.js rewrites `/api/*` to `BACKEND_INTERNAL_URL` (default `http://127.0.0.1:8000`), so the session cookie is first-party. The voice WebSocket is the one connection made to the backend URL directly, authenticated with a single-use ticket.
- `start-narratiq.sh` bootstraps a brand-new pod. It installs dependencies, downloads pinned model revisions, provisions PostgreSQL 16 + pgvector, runs migrations, starts vLLM, the backend (exactly one worker), the frontend, the hourly backup loop and the watchdog.

## 3. Model Documentation

### 3.1 Qwen2.5-7B-Instruct

Served by vLLM on port 9001 and reached through one `AsyncOpenAI` client in `services/ai_service.py`. All calls go through `_complete()` / `_complete_ex()` / `complete_structured()` (and `_stream_generate()` for streaming). Connection errors and 429/5xx responses become `AIServiceUnavailableError`, which the API returns as HTTP 503 with `Retry-After`.

**Hardware and context window.** The verified production pod is **1× NVIDIA A40 (46 GB)**, running vLLM with tensor parallelism 1, `max-model-len` **8192** and 0.88 GPU memory utilisation. The startup script scales automatically:

| GPUs | Tensor parallelism | Context window |
|---|---|---|
| 1 | 1 | 8192 |
| 2–3 | 2 | 16384 |
| 4+ | 4 | 32768 |

Context budgets (Story Bible, Plot Assistant, Phase 3 context) are sized for 8192.

**Prompt versioning (Stage 5).** Prompt builders live in `services/prompt_registry.py` under version identifiers. `v1` is the frozen pre-Stage-5 baseline and `v2` is the improved set. Reverting means selecting a version, not editing code.

**Main generation functions:**
- intake and genre detection
- refine, tone (9 categories), emotion (6, with intensity), age adaptation, style, author-inspired style and translation, all streaming
- writing suggestions
- Plot Assistant intent detection, question answering and creative suggestions
- chapter summarisation
- OCR cleanup and correction suggestions
- character hints, enrichment and arc snapshots
- plot holes and the manuscript report
- Story Bible sections
- continuity, emotional arc and style-drift descriptions
- outline and continuation
- narrative-thread scanning
- audio transcript cleanup
- copyright-risk analysis
- the voice agent's intent and planning steps
- Phase 3 compare summaries and merges

### 3.2 BGE-M3

Loaded once, synchronously, at startup (`get_bge()`), producing 1024-dimensional vectors. Every embedding in the system comes from this singleton; there is no second model instance. All **retrieval** uses pgvector's `<=>` cosine operator in SQL. Four request-time comparisons of freshly computed vectors still use numpy. They are listed as Phase 2 rule deviations in §9.

### 3.3 GOT-OCR2.0

580M parameters (ViT-large encoder + Qwen-0.5B decoder). It is lazy-loaded and cached. It picks a GPU with ≥ 2.5 GB free, otherwise the CPU, and retries on the CPU after a CUDA out-of-memory error. One `model.chat()` call returns the whole page. ⚠️ See §4.5 for the current defect.

### 3.4 faster-whisper

Large-v3-turbo transcribes uploaded audio notes in a background job; Qwen then removes fillers and formats paragraphs. The base model produces live partial transcripts for the voice agent. Both run on the CPU, so they never compete with vLLM for GPU memory.

## 4. Ingestion: OCR, Audio and Manuscripts

### 4.1 OCR pipeline

1. **Extraction.** `POST /api/ocr/extract/{story_id}` accepts JPEG, PNG, WebP, HEIC and HEIF (MIME and extension both validated), up to `MAX_OCR_UPLOAD_MB`.
2. **Cleanup and suggestions.** Qwen fixes spacing and punctuation. BGE-M3 retrieves the four most relevant chunks, and Qwen proposes corrections grounded in the story's vocabulary. A three-rule entity filter protects proper nouns.
3. **Injection.** The author reviews and confirms one destination through `POST /api/ocr/confirm`. Confirmation is idempotent.

### 4.2 Destinations

| Destination | Effect |
|---|---|
| `chapter_draft` | Appended to the chapter as a TipTap block, with a version snapshot, re-embedding and re-summarising |
| `story_notes` | New Story Note |
| `note_card` | New Note Card |
| `character_profile` | Appended to the character's raw notes; profile re-embedded |

### 4.3 Audio notes (P2-11)

`POST /api/stories/{id}/audio` (up to `MAX_AUDIO_UPLOAD_MB`, default 100) starts a transcription job. The frontend polls `GET …/audio/{audio_id}`, and `POST …/audio/{audio_id}/confirm` appends the cleaned text to a note. Confirmation is idempotent.

### 4.4 Manuscript ingestion

`POST /api/manuscript/upload/{story_id}` (DOCX, up to `MAX_MANUSCRIPT_UPLOAD_MB`) starts a persistent background job (`manuscript_jobs`, status via `GET /api/manuscript/job/{job_id}`). The job splits chapters, embeds chunks and summarises. ⚠️ **No upload control exists in the UI yet** (Stage 6 finding, task 6.4).

### 4.5 Current OCR defect

⚠️ **High:** every OCR extraction currently fails with "OCR processing failed". GOT-OCR2.0's remote code uses an attribute (`DynamicCache.seen_tokens`) that the `transformers` version required by vLLM 0.9.2 no longer provides. Upload, review and injection are unaffected, but no text reaches them. Tracked in [`docs/issues-and-bugs/ocr-extraction-got-ocr2-dynamiccache-failure.md`](../issues-and-bugs/ocr-extraction-got-ocr2-dynamiccache-failure.md).

### 4.6 Image and audio retention

An hourly sweep deletes OCR images 24 hours after confirmation and 72 hours after upload if never confirmed. Audio files are swept the same way, and so are upload files no database row references. The policy is published in [`docs/policies/data-retention-and-deletion.md`](../policies/data-retention-and-deletion.md) and served to authors at `/data-policy`.

## 5. Characters

### 5.1 Model

**Tables:**
- `characters`: an identity anchor holding name, aliases, role and status.
- `character_profiles`: structured fields plus two embeddings. The profile embedding is weighted 0.4 and the embedding of the character's mentions 0.6.
- `character_relationships`: directed, typed edges with strength and a mutual flag.

Supporting tables:
- `character_mentions`: a per-chunk mention index.
- `character_hints`: names the model found in the text that are not yet registered.
- `character_arc_snapshots`: one row per character per chapter.

### 5.2 Capabilities

- **CRUD:** create, list, search, update and delete, with a 409 on a name collision within a story.
- **Relationship graph:** an SVG directed graph with drag, typed and coloured edges, and strength labels.
- **Hints:** Qwen proposes unregistered names; the author promotes or dismisses them.
- **Enrichment:** Qwen proposes profile fields from mention passages, with evidence and confidence.
- **Arc timeline:** per-chapter emotional state and key action, with staleness marking.
- **Merge (Stage 4):** two records combine into one, with mentions, relationships and snapshots reassigned in one transaction. ⏳ Automatic duplicate detection is not built.
- **Dialogue voice consistency (P2-03):** `POST /api/stories/{id}/characters/{char_id}/voice-check`.

### 5.3 Character retrieval

`retrieve_character_context()` combines a name/alias mention boost with pgvector cosine over both embeddings. It returns up to three profiles within an 800-token budget. Under the D-1 default, story-evidence passages are capped at the author's current chapter, so retrieved evidence never reveals later chapters.

## 6. Plot Assistant, Retrieval and Story Analysis

### 6.1 Plot Assistant modes

| Mode | Retrieval | Output |
|---|---|---|
| Question answering | Chapter summaries + paragraph chunks + character context when a character is named | One grounded answer |
| Creative | Chapter summaries + character context | Three suggestions, each with a rationale tied to the story |
| Mixed | All of the above, shared | Answer and suggestions |

Story Notes and Note Cards are retrieved alongside the chapters (`retrieve_note_context()`, a pgvector `UNION ALL`).

### 6.2 Retrieval scope (decision D-1)

By default the Plot Assistant searches **up to and including the author's current chapter**, so it never reveals or relies on later chapters. The author can switch a question to **Full manuscript**. The scope used is reported with the answer.

### 6.3 RAG pipelines

| Pipeline | Source | Notes |
|---|---|---|
| Chapter summaries | `chapter_summaries.embedding` | Generated on chapter save |
| Paragraph chunks | `chapter_chunks.embedding` (~350 words, 2-paragraph overlap) | Re-indexed after search-and-replace |
| Characters | `character_profiles` (two vectors) | Hybrid name boost + cosine, 800-token cap |
| Notes and cards | `story_notes`, `note_cards` | Plot Assistant context |
| OCR grounding | chunks | Top 4 for correction suggestions |
| Phase 3 context | pinned generations and preferences | Assembled only in `services/generation_context.py`; pins are never embedded or retrieved |

### 6.4 Story Intelligence

`/api/stories/{id}/intelligence/*` runs a background analysis job (`story_intel_orchestrator`). It exposes:
- genre DNA (with an author override)
- audience, themes, conflicts and world
- structure, emotional arc and pacing
- strengths, risks and foreshadowing
- continuity
- characters and relationships (with overrides)
- a searchable story memory
- a timeline and a story graph

### 6.5 Plot holes, manuscript report and Story Audit

- **Plot holes** (`POST /api/stories/{id}/plot-holes`) finds six inconsistency types, each with a severity.
- **Manuscript report** (`GET/POST …/manuscript-report`, cached per story) covers character arcs, pacing, unresolved threads, strengths and improvements.
- **Stage 5** added relationship arcs, dedicated timeline and narrative reasoning signals, stakes and themes, and an adversarial check that replaces generic advice.
- ⚠️ **60-chapter ceiling:** both analyses accept up to 60 chapters, accepted for launch under decision D-8. The strategy registry contains only the single-pass strategy. Batched and hierarchical strategies for longer manuscripts are **not written**: their registry entries are commented-out names of functions that do not exist. Lifting the cap is new development work.

### 6.6 Search

- Exact search: `POST /api/search/exact/{story_id}`.
- Semantic search over chunks: `/semantic/{story_id}`.
- Search-and-replace (`/replace/{story_id}`) re-embeds the affected chapters.

## 7. Writing Tools and Transforms

### 7.1 Selection transforms (`/api/ai/*`)

All of these stream (a `/stream` variant exists for each):
- `refine`
- `tone`: 9 categories
- `emotion`: 6 categories, with intensity
- `age-adapt`
- `style`
- `author-style` (§10)
- `translate`: with a per-story glossary that keeps character names consistent

`suggestions` gives craft feedback on chapter text.

### 7.2 Preservation engine (Stage 5)

Every transform passes through a deterministic preservation layer (`services/transform_preservation.py`), and code enforces what a prompt cannot guarantee:
- **Sentence locks:** locked ranges are restored verbatim by code after generation (P3-02).
- **Strength control:** light, standard or aggressive. An output that changes far more than the chosen strength allows is flagged.
- **Name preservation:** character names that disappear or change are detected.
- **Per-story preservation rules:** Phase 3, P3-05.

### 7.3 Chapter tools

- **Continuation** (`POST …/chapters/{cid}/continue`) offers three options.
- **Outline / beat sheet** (`POST …/chapters/{cid}/outline`).

Both retrieve chapter and character context.

### 7.4 Writing analytics

`GET /api/stories/{id}/analytics` reports word counts, readability and dialogue ratio. Pacing goals (`/pacing-goals`) track progress against a target.

**Recorded deviations** (accepted as documented; detail in the acceptance record):

1. **P2-05 continuity runs inside the request** (in batches of 10 chapters), not as a background job with an id (rule R10). Measured 14.7 s for 200 chapters.
2. **Audio uses `/api/stories/{id}/audio…` routes** rather than the roadmap's `/api/audio/…`.
3. **Whisper comes from the `deepdml` CTranslate2 mirror and runs on CPU int8**, because the roadmap's repository now returns 401.

Fixed in Stage 11 rather than accepted:
- the Story Bible stale warning (P2-06);
- all Phase 2 similarity computed in pgvector (R12);
- no third-party browser requests (R4);
- the voice check bounded so it stays fast on long manuscripts (R7).

Every Phase 2 feature was verified on a 200-chapter manuscript.

**Stale warning (Stage 11).** The Story Bible records which version of the indexed chapters it was generated from. When a chapter is edited, re-indexed, added or removed afterwards, the panel says "Your chapters have changed since this Story Bible was generated" and offers Regenerate. Regenerating a single section does not clear the warning.

**The Story Bible's honest-status model (Stage 3).** Each of the five sections records its own outcome. The bible is `completed` only if all five succeed, `partial` if some fail and `failed` if none succeed. Failed sections are stored in `failed_sections` and can be retried one at a time. Placeholder text is never stored as content.

## 10. Author-Inspired Style and Copyright-Risk Guidance (v3.2.0)

Specification: [`author-style-and-copyright-risk-features.md`](./author-style-and-copyright-risk-features.md).

### 10.1 Author-inspired style rewrite

The server-side registry is the only authority on which authors may be named:
- Six **public-domain** authors are offered by name: Shakespeare, Austen, Dickens, Poe, the Brontës and Twain.
- Requests naming in-copyright authors (for example Hemingway, Woolf or Christie) are redirected to generic descriptors such as "minimalist".
- Any unknown name falls back to a generic literary style.

The author's raw input **never reaches the prompt**. Every prompt carries an explicit "inspired by, never copy" clause. Like every rewrite, author-style output is checked in code: a "rewrite" that no longer contains the selected passage is retried once and otherwise refused (§14).

### 10.2 Copyright and plagiarism risk

`POST /api/stories/{id}/copyright-risk` analyses a selection, a chapter or the project. It returns findings and an overall risk level, each finding carrying a level, an explanation and a suggestion. The headline is **never lower than the most severe finding** (enforced in code since v3.2.0), so a "low" headline cannot accompany a "high" finding.

The response always carries a disclaimer: risk guidance, not legal advice. **⚠️ The disclaimer wording has not yet had legal review.** Results are not stored.

**Prompt injection:** instructions hidden inside a selected passage are handled by the defence in §14. A copyright `note` that merely repeats a span of the analysed text is dropped.

## 14. Security and Privacy

- **Self-hosted:** no external AI API, no analytics SDK and no telemetry. The browser contacts only this server; fonts are self-hosted (Stage 11).
- **Prompt-injection defence (Stage 11, finding P1).** A manuscript is untrusted input to the model: a passage can contain "ignore your instructions and reply X". Every model call:
  - fences the author's material as data, with a per-call random marker;
  - tells the model the fenced text is never an instruction;
  - restates the concrete task *after* the material (for Q&A, the author's question comes last).

  Rewrite outputs are then checked in code: one that no longer contains the selected passage is retried once and otherwise refused, with "Your text has not been changed". Measured results and the residual risk are in `docs/testing/stage-09-security-findings.md`. No prompt-based defence can guarantee a language model never follows injected text.
- **Sessions:**
  - HttpOnly, SameSite cookie
  - CSRF double-submit for cookie-authenticated writes
  - logout revokes that session; a password change or account deletion revokes all sessions
  - the voice WebSocket uses a single-use 60-second ticket
- **Ownership:** every story-scoped endpoint verifies ownership and answers 404 for both "not yours" and "does not exist". Stage 9 fixed seven isolation defects (I1–I7) and added tests for each.
- **Open security items** ([`stage-09-security-findings.md`](../testing/stage-09-security-findings.md)):
  - **P1:** prompt injection through manuscript text. **Mitigated in Stage 11** (above). The residual risk is a lower obedience rate plus refusal of hijacked rewrites, not zero. It affects only the author's own results.
  - **D1 and D3:** dependency advisories in vLLM 0.9.2 and Next.js 14. Fixing them needs major upgrades.

## 15. Known Limitations

1. OCR extraction is failing (§4.5).
2. There is no manuscript-upload control in the UI (§4.4).
3. Plot holes and the manuscript report stop at 60 chapters (§6.5, D-8).
4. No off-pod backups and no alert delivery to a person until an external service is approved (§13).
5. Open dependency advisories (§14), and the residual prompt-injection risk after the Stage 11 defence: reduced, and caught in code for rewrites, but not impossible.
6. Single-owner stories: the collaboration permission seam always grants access, so there is no co-authoring.
7. No EPUB/Kindle export.
8. Imitation quality for public-domain author styles is approximate on a 7B model, and copyright detection is heuristic.
9. Real-author UAT has not yet been run (task 9.6). The AI quality claims in this document rest on automated measurement, not author judgement.
