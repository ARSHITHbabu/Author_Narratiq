# Backup and restore runbook

**Stage 10, task 10.1 (production gap PG-02).** Status as of 2026-09-29: automated on-pod backups, content-integrity verification and restore rehearsal are implemented. **The off-pod copy is deferred** (decision S10-B: no external storage provider in Stage 10). Until it exists, these backups do **not** protect against loss of the RunPod network volume itself.

---

## 1. What is backed up

Each backup is one **set** of files in `/workspace/backups` (the RunPod network volume), all written by `scripts/backup_database.sh` (hourly loop and manual runs) or `scripts/startup_backup.sh` (before every schema migration):

| File | Contents |
|---|---|
| `narratiq-<stamp>.dump` | `pg_dump` custom-format archive of the whole database |
| `narratiq-<stamp>.manifest.json` | Integrity manifest of the **same snapshot** (see §3) |
| `narratiq-uploads-<stamp>.tar.gz` | Every file under `backend/uploads/` (OCR page images, audio uploads) |
| `narratiq-globals-<stamp>.sql` | Role definitions, without password hashes |
| `narratiq-globals-<stamp>.sql.sha256` | SHA-256 of the globals file |
| `narratiq-<stamp>.SHA256SUMS` | SHA-256 of the four files above |
| `narratiq-<stamp>.dump.sha256` | SHA-256 of the dump (kept for older tooling) |

**Not in the dump:** the *rows* of `ai_generation_pins` (Phase 3 decision D9 — temporary AI drafts, never manuscript content; the table definition is dumped, so a restore recreates it empty).

**Not backed up by these scripts:** `backend/.env` (it holds `SECRET_KEY`, `OPS_TOKEN` and the DB password). It sits on the same volume as the backups, so a copy there adds nothing. It is regenerated by `start-narratiq.sh` on a fresh pod, **but a new `SECRET_KEY` signs every author out once** (sessions are signed with it); keep a copy of `SECRET_KEY` in your own password manager. Model weights are not backed up either — they are re-downloaded at the pinned revisions (`docs/operations/model-versions.md`).

## 2. Schedule and retention

| When | What | Where configured |
|---|---|---|
| Every start of `start-narratiq.sh` | Pre-migration backup: **required** before any schema change (aborts the start if it cannot be made); otherwise taken only when the newest backup is older than 24 h (`NARRATIQ_BACKUP_MAX_AGE_HOURS`). Also runs the empty-database guard (§4a) | `scripts/startup_backup.sh` |
| Every hour | Backup set. The loop waits one interval first, so the first hourly set lands about an hour after start | `NARRATIQ_PERIODIC_BACKUP_INTERVAL_HOURS=1` |
| After every hourly backup | Rotation: keep the newest **24** sets + the newest set of each of the last **7** days; never a set with a `narratiq-<stamp>.keep` marker, never the newest set that passed verification | `scripts/backup_retention.py`, `NARRATIQ_BACKUP_KEEP_RECENT`, `NARRATIQ_BACKUP_KEEP_DAILY_DAYS` |
| First cycle, then every 24 h | Restore verification of the newest set (§3) | `NARRATIQ_BACKUP_VERIFY_EVERY_HOURS=24` |

Log: `/workspace/logs/periodic-backup.log` (persistent). Record of startup backups: `/workspace/backups/BACKUP-RECORD.txt`. A failed step is logged and alerted (§5); it never stops the next scheduled backup.

To keep a set forever (e.g. before a risky operation): `touch /workspace/backups/narratiq-<stamp>.keep`.

## 3. How integrity is verified

A row count proves a table is not empty; it does not prove the data is right. `scripts/backup_snapshot.py` takes the dump **inside one exported database snapshot** (`pg_dump --snapshot=`) and computes the manifest from that same snapshot, so the two always agree even while authors write:

* per table: row count and an md5 over **every column of every row** (pgvector embeddings included), in primary-key byte order;
* chapter text: an md5 over every chapter's id and content hash;
* embeddings: how many vectors each of the 9 vector columns holds;
* uploads: SHA-256 of every file, taken from the bytes written into the archive;
* the Alembic revision;
* a warning count of database rows that point at an upload file missing from disk.

`scripts/verify_backup.py` then proves the set **restores**:

1. every checksum in `SHA256SUMS` matches;
2. the archive's table of contents is readable;
3. the dump is restored into the scratch database **`narratiq_restorecheck`** — the only database name the script ever creates or drops;
4. the restored database is fingerprinted the same way and must equal the manifest **table by table** — row counts, content hashes, chapter text, embedding counts, schema revision — and `ai_generation_pins` must restore empty;
5. the uploads archive is unpacked and every file's SHA-256 must equal the manifest.

The result goes to `/workspace/backups/LAST-VERIFY.json` (and is appended to `VERIFY-RECORD.jsonl`). Exit code 0 = PASS, 1 = FAIL.

Run it by hand at any time (read-only for the live database):

```bash
cd /workspace/narratiq-ai
set -a; eval "$(python3 - <<'EOF'
from urllib.parse import urlsplit
u=[l.split('=',1)[1].strip() for l in open('backend/.env') if l.startswith('DATABASE_URL=')][0]
p=urlsplit('//'+u.split('://',1)[1])
print(f"PGHOST={p.hostname} PGPORT={p.port or 5432} PGUSER={p.username} PGPASSWORD={p.password} PGDATABASE={p.path[1:]}")
EOF
)"; set +a
python3 scripts/verify_backup.py                 # newest set
python3 scripts/verify_backup.py --set narratiq-20260929T120000Z
```

Tests: `scripts/tests/test_backup_pipeline.py` proves a real set verifies PASS and that altered table content, a changed upload file and a corrupted archive each make verification FAIL.

## 4. Restore procedure (the database is lost or damaged)

> Restoring **replaces** the live database. It is always a deliberate, manual operation — nothing restores automatically. Read every step first.

1. **Stop writes.** `pkill -f 'uvicorn main:app'` (the frontend may keep running; it will show that the service is unavailable). Stop the loop so it does not back up a half-restored database: `kill "$(cat /tmp/narratiq-logs/periodic-backup.pid)"`.
2. **Choose the set.** `ls -1t /workspace/backups/narratiq-2*.SHA256SUMS | head`. Prefer the newest set; check `LAST-VERIFY.json` — a set that already passed verification is the safest choice.
3. **Verify it before trusting it:** `python3 scripts/verify_backup.py --set narratiq-<stamp>` (§3). Do not restore a set that FAILs.
4. **If the database still holds anything**, keep it first: `bash scripts/backup_database.sh` (a new set — it may be the only copy of the most recent writes), then mark it `touch …/narratiq-<new stamp>.keep`.
   > **Before step 5, clear the connection variables:** `unset PGHOST PGPORT PGUSER PGPASSWORD PGDATABASE`.
   > Step 3 needs them (exported as in §3), but `su postgres -c` keeps the caller's environment. With them
   > still set, step 6's `dropdb` runs as the database owner `narratiq` and **succeeds**, and `createdb`
   > then fails with "permission denied to create database". The database is gone and the restore has not
   > started. Found in the Stage 12 Tranche 3 rehearsal (2026-10-03). If it happens, unset the variables
   > and continue from step 6. The verified set is unaffected.
5. **Fresh pod only — roles:** `su postgres -c "psql -f /workspace/backups/narratiq-globals-<stamp>.sql"` (role *definitions*; the password comes from `backend/.env`, which `start-narratiq.sh` rewrites).
6. **Restore the database** (as the database superuser, streaming the dump so its file mode can stay 600):

   ```bash
   su postgres -c "dropdb --if-exists narratiq && createdb -O narratiq narratiq \
       && psql -d narratiq -c 'CREATE EXTENSION IF NOT EXISTS vector'"
   pg_restore --list /workspace/backups/narratiq-<stamp>.dump | grep -v ' EXTENSION ' > /tmp/restore.list
   su postgres -c "pg_restore --no-owner --role=narratiq --exit-on-error -L /tmp/restore.list -d narratiq" \
       < /workspace/backups/narratiq-<stamp>.dump
   ```
7. **Restore uploads:** `mkdir -p backend/uploads && tar -xzf /workspace/backups/narratiq-uploads-<stamp>.tar.gz -C backend/uploads`.
8. **Validate against the manifest** — the same check the verifier runs, now on the live database (export the connection variables again, as in §3):

   ```bash
   python3 scripts/backup_snapshot.py manifest > /tmp/live-manifest.json
   python3 - <<'EOF'
   import json
   want = json.load(open('/workspace/backups/narratiq-<stamp>.manifest.json'))
   got = json.load(open('/tmp/live-manifest.json'))
   bad = [t for t, w in want['tables'].items() if not w['excluded'] and got['tables'].get(t, {}).get('content_md5') != w['content_md5']]
   print('MATCH' if not bad and want['checks'] == got['checks'] else f'DIFFERENT: {bad}')
   EOF
   ```
   Then spot-check by hand: open one manuscript in the app and read its last chapter.
9. **Start the stack:** `bash start-narratiq.sh`. It takes a fresh pre-migration backup, applies any newer migrations, and restarts the backup loop and the watchdog.

### 4a. The empty-database guard (startup refuses to run)

`start-narratiq.sh` stops before any migration, printing **"UNEXPECTED EMPTY DATABASE — STARTUP ABORTED"**, when the live database holds no author rows **and** a valid backup set whose own manifest shows author data exists (`scripts/startup_backup.sh`, `scripts/backup_evidence.py`). The database lives on the container layer (`storage-and-persistence.md` §4.1), so this is what a pod restart that wiped it looks like. Backups of an empty database never trigger it, and an older data backup is never hidden by newer empty ones.

* **Data was lost:** do not override. Restore with §4 above (step 9's `start-narratiq.sh` then finds data and continues). The guard's own message prints a checksum check and points here.
* **Restoring a set that is itself empty, or an intentional fresh start** (the data was deleted on purpose, e.g. a disposable account removed through `DELETE /api/auth/account`): the guard cannot tell deliberate deletion from loss (an open owner decision). Start once with the exact phrase — `1`/`true` are refused:

  ```bash
  NARRATIQ_ACKNOWLEDGE_EMPTY_RESTART=yes-start-empty-intentionally bash start-narratiq.sh
  ```
  Set it on the command line only, **never** in `backend/.env` or the RunPod UI, where it would silently disable the guard for every later restart. Every later start blocks again while backup sets holding the old data remain in `/workspace/backups`. Retiring those sets is a deliberate operator decision, never automatic; the open owner decision on telling deletion from loss would remove the need.
* **A brand-new pod with no `/workspace/backups`** passes the guard: there is no evidence of earlier data.

## 5. Monitoring of the backups

The watchdog (`docs/operations/monitoring-and-alerting.md`) raises:

* `backup_stale` — the newest on-pod dump is older than 3 h (`NARRATIQ_ALERT_BACKUP_MAX_AGE_HOURS`);
* `backup_verify_failed` — `LAST-VERIFY.json` says FAIL.

`/api/ops/metrics` → `backups` shows the newest dump's age, the last verification and the off-pod status.

## 6. RPO and RTO

These are **engineering targets and local measurements**, not a claim that full disaster recovery is achieved: with the off-pod copy deferred, loss of the network volume loses the backups too.

| | Target | Status (2026-09-29; RTO updated 2026-10-03) |
|---|---|---|
| **RPO** — data an author can lose | **≤ 1 hour** for loss of the database (pod restart, container rebuild, corruption) | Met by design on-pod: hourly sets + a backup before every migration. **Not met for loss of the network volume** — needs the off-pod copy. |
| **RTO** — time to have authors writing again | **≤ 2 hours** from a fresh pod | **Met, measured end to end 2026-10-03** (Stage 12 Tranche 3, A24, pod `x0smrkvs4n6wpk`). Fresh-pod bring-up with `start-narratiq.sh`: 14 min 35 s (installs, ~22 GB of pinned model downloads, migrations, services). Restore (§4 steps 1–8 on a 57-table set): about 25 s of commands. Restart (step 9): 337 s. Total **about 21 minutes** from a fresh pod, **about 6.3 minutes** on a running pod. Evidence: `docs/testing/stage-12/tranche3/gates-1-2-7.md`. Stage 10 had timed only the restore step (`restore_seconds` in `LAST-VERIFY.json`). |

## 7. Off-pod copy (deferred)

Decision S10-B: no external storage provider is configured in Stage 10. The loop is ready for one: set `NARRATIQ_OFFPOD_COMMAND` to any command, and after every backup it is run with the new set's five file paths as arguments. Its outcome is recorded in `LAST-OFFPOD.json` (today: `not_configured`); a failing command never affects local backups. When a destination is chosen, the recommended shape is to encrypt each file with a public key whose private key never touches the pod, then upload — so the provider only holds ciphertext. The checklist items that need a real off-pod destination stay open until then.
